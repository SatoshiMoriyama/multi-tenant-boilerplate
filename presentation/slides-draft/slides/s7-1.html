7. コンピュート・API: tenantId を実行環境まで持ち込む

Lambda テナント分離モード（2025-11 新機能）

  • OFF: 1 つの実行環境を複数テナントが使い回す（メモリ越しの汚染リスク）
  • ON: X-Amz-Tenant-Id ごとに Firecracker 実行環境が分かれる

設定: TenancyConfig.TenantIsolationMode: PER_TENANT（関数作成時のみ）

取得: context.tenantId ／ JSON ログに tenantId 自動付与

Pool 型 Lambda の長年の弱点は、同一実行環境が複数テナントで再利用されメモリに前テナントのデータが残りうること。これに AWS が 2025-11 に正面から回答したのがテナント分離モード。 有効化すると Invoke 時に tenant-id（API では X-Amz-Tenant-Id ヘッダー）が必須になり、同一テナントの実行環境だけが再利用される。省略すると InvalidParameterValueException。 トレードオフ①: 全テナントが同一実行ロールを共有する点は変わらない。細粒度権限が要るなら上流からテナントスコープの一時クレデンシャル（STS）を渡す。 トレードオフ②: 実行環境を分けるのでコールドスタート頻度とコストが増える。多数テナント×低頻度だと効きが悪い。 補足: Powertools for AWS Lambda で Logger / Tracer / Metrics に tenantId を一貫注入できる。
