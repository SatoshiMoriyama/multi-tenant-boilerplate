6. 認証・認可: 信用できる tenantId はどこで作るか

Cognito ── テナント分離の 3 方式

方式特徴分離の強さ / 運用
user-poolテナントごとに別プール（上限デフォルト 1,000）強い / 重い（Silo 寄り）
app-client単一プール内でテナント別クライアント中 / 軽い（Pool 寄り）
custom scope（M2M）リソースサーバのカスタムスコープ—

どの方式でも肝: pre token generation Lambda trigger でトークンに tenantId を注入

Cognito は OIDC の IdP。公式が3方式を挙げる。選択がそのまま分離の強さとコストに効く。 user-pool はプール数の上限とオンボーディングの重さがトレードオフ。app-client は単一ユーザープロファイル基盤を保ちつつ callback/logout URL をテナントのオリジンに限定。 肝は pre token generation trigger での tenantId クレーム注入。これが「信用できる tenantId」の発生源。https://aws.amazon.com/tags 名前空間に載せれば後段の IAM ABAC（session tags）へ橋渡しできる。 設計の勘所: tenantId を載せる属性は不変（mutable: false）。可変だとユーザーが書き換えて別テナントのトークンを得られる。所属は作成時に確定し以後変えさせない。 ボイラープレートの実例: app-client 方式を採用。1 User Pool 共有、テナントごとに App Client を分けて callback を自テナントに限定。custom:tenantId は mutable: false。
